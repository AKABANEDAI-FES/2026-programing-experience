# 現在の要件定義で不足している点

この文書は、現行の `docs/` 配下の要件定義をもとに、本番実装へ進む前に追加で決める必要がある事項を整理する。

## 1. 体験全体の成功条件

- 来場者が何分程度で体験を完了する想定なのかが未定義。
- スタッフがどの画面で、どの程度サポートする前提なのかが未定義。
- 「子どもが迷わない」ことを判断する具体的な基準がない。
- 8 台の制作 PC が同時に使われる場合の待ち行列、交代タイミング、途中離脱時の扱いが未定義。
- 体験が成功した状態を、参加者側・投影側・スタッフ側それぞれでどう確認するかが未定義。

## 2. 画面遷移とリセット

- 画面遷移は一方通行とされているが、誤操作時の復旧手段が未定義。
- 完了画面から 5 秒でホームへ戻る仕様はあるが、API 送信失敗時にどの画面へ残すかが未定義。
- スタッフ用の強制リセット画面・隠し操作・認証方法が未定義。
- ブラウザリロード、タブを閉じた場合、PC がスリープした場合の復帰仕様が未定義。

## 3. お絵かき・塗り絵

- `Canvas` を使わない方針はあるが、SVG の保存形式、座標系、線の滑らかさ、消しゴム仕様が未定義。
- `frontend-requirements.md` では SVG 等、`backend-api-spec.md` では PNG base64 とされており、画像形式が一致していない。
- API フィールド名 `image_base64` が SVG Data URL も受けるのか、PNG 専用なのかが未定義。
- イニャーの正式な下絵素材、描画可能範囲、塗り残し許容、色パレットが未定義。
- 空白の絵、極端に小さい絵、画面全体を塗りつぶした絵を許可するかが未定義。
- Undo、Clear、ペン色、線幅など、来場者が自然に期待する基本操作の採否が未定義。

## 4. Blockly とプログラム仕様

- 「ループさせる動きブロック」と「セリフブロック」はあるが、正式なブロック一覧が未定義。
- `shared/src/release.ts` では `motion: string` になっており、許可する motion 値が未定義。
- コマンド JSON の正式スキーマ、順序の意味、同じ種類のブロックを複数置いた場合の解釈が未定義。
- 最大 5 個の制限を、Blockly UI 上で禁止するのか、送信時にエラーにするのかが未定義。
- セリフの最大文字数、使用可能文字、不適切語への対応が未定義。
- 動きの速度、範囲、画面端での挙動、複数コマンドの合成ルールが未定義。
- `react-blockly` を使う方針はあるが、現在の React バージョンとの互換性確認方針が未定義。

## 5. 放流 API とデータ保存

- `POST /api/release` の成功レスポンスに保存後の ID や取得 URL を返すかが未定義。
- 400 系エラーの種類、バリデーション内容、ユーザーに表示する文言が未定義。
- R2 に保存するオブジェクト構造、ファイル名、content type、メタデータが未定義。
- 画像とプログラムを同じオブジェクトに保存するのか、別オブジェクトに分けるのかが未定義。
- 投稿済み作品を投影画面が取得する API が未定義。
- 保存に成功したが通知に失敗した場合、または通知に成功したが保存に失敗した場合の扱いが未定義。

## 6. 投影画面

- 投影画面の URL、起動方法、制作 PC 画面との分離方法が未定義。
- 最大 30 匹の FIFO は定義されているが、削除の責務が backend か frontend か未定義。
- 投影画面を再読み込みしたとき、過去の作品を再表示するのか、空から始めるのかが未定義。
- 各コマンドが投影画面でどのようなアニメーションになるかが未定義。
- 画面解像度、プロジェクター比率、ブラウザのズーム、全画面表示の前提が未定義。
- 多数の作品、巨大な画像、長時間稼働時のパフォーマンス基準が未定義。

## 7. リアルタイム通信

- WebSocket、Durable Objects、SSE が候補として書かれているが、正式な方式が未決定。
- 接続が切れた場合の再接続、重複通知、順序保証、取りこぼし復旧が未定義。
- 投影画面が複数台ある場合に同じ通知をどう配信するかが未定義。
- ローカル開発時、本番時、当日会場ネットワークでの接続 URL と CORS 設定が未定義。

## 8. セキュリティ・安全対策

- キオスク制御として右クリック、F5、F12 の禁止が挙がっているが、OS・ブラウザ設定とアプリ側制御の分担が未定義。
- 投稿内容の安全対策、特に不適切な絵やセリフへの対応が未定義。
- API の認証・レート制限・会場外からの投稿防止策が未定義。
- CORS の本番許可 origin が未定義。
- 管理者画面を作る場合の認証、操作ログ、誤操作防止が未定義。

## 9. 障害対応と運用

- `当日の流れ.md` ではトラブル対応が「各自で対応」とされており、具体手順が不足している。
- API 障害、投影 PC 障害、制作 PC 障害、ネットワーク障害ごとの復旧手順が未定義。
- 作品送信に失敗した参加者へ、スタッフがどう案内するかが未定義。
- 当日前の動作確認手順、チェックリスト、担当者、予備 PC の有無が未定義。
- ログをどこで確認し、障害後に何を調査できるようにするかが未定義。

## 10. 非機能要件

- 対応ブラウザ、OS、画面サイズ、マウス入力の詳細条件が未定義。
- 送信 API の応答時間、投影画面への反映時間、同時利用時の性能目標が未定義。
- 長時間稼働時のメモリ使用量、R2 保存容量、Cloudflare 利用制限への考慮が未定義。
- アクセシビリティ、音声利用の有無、会場騒音下での視認性が未定義。
- 開発・ステージング・本番環境の切り替え方法が未定義。

## 11. 先に確定したい優先事項

1. 画像形式を SVG Data URL にするか、PNG base64 にするか。
2. Blockly の正式なブロック一覧と `commands` の JSON スキーマ。
3. 投影画面の URL と、投稿済み作品を取得する API。
4. リアルタイム通信方式と、切断時の復旧方針。
5. スタッフ用リセットと障害時オペレーション。
6. イニャー塗り絵の正式素材と利用条件。
