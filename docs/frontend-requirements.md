# 学祭展示「プログラミング体験会」フロントエンド要件定義

## 1. アプリケーションの目的と基本方針
* **対象端末:** 受付・制作PC（計8台）および標準的なマウス
* **目的:** 来場者が迷わず「1画面1タスク」でキャラクターを描き、動きをプログラミングして大画面へ放流する。
* **画面遷移の基本ルール:** お絵かきからプログラミングへは**「完全一方通行」**とし、前の画面に戻るボタンは配置しない（体験時間の管理は近くのスタッフがアナログで行うため、システム側でのタイマーは設けない）。
* **スタイリング方針:** コンポーネントごとのスタイリングには **CSS Modules** を使用する。

## 2. 状態管理（State）の定義
*React内で保持し、画面間で引き回すデータの定義。*

| State名 | 型 | 役割 |
| :--- | :--- | :--- |
| `step` | `number` (1〜4) | 現在の画面位置を制御する。 |
| `drawMode` | `'free' \| 'coloring'` | 選択されたモード（自由なお絵かきか、イニャーの塗り絵か）。 |
| `imageData` | `string` | SVG等で保持される最終的な画像データ。 |
| `program` | `object[]` (JSON) | Blocklyから出力された、ユーザーが選択した動き・セリフのデータ。 |

## 3. 各画面のUI要件・機能要件

### 【画面①】ホーム画面
* **機能:** アプリのスタート画面。「自由にお絵かき」と「イニャーの塗り絵」の2つのボタンを配置し、体験を開始する入り口兼モード選択画面となる。
* **遷移トリガー:** どちらかのボタン押下でモード（`drawMode`）を決定し、画面②へ進む。

### 【画面②】お絵かき・塗り絵画面（※Canvas機能は使用しない）
* **機能:**
  * **描画機能:** 画面①で選ばれたモードに応じたキャンバス（白紙または下絵あり）を表示。マウスドラッグで線を描き、消しゴムで消す軽量なペイント機能（Canvas機能は使わず、SVGのPath要素などを利用して実装する）。
* **遷移トリガー:** 「次へ」押下時、描画状態をデータ化して `imageData` に保存し、画面③へ進む（戻る操作は不可）。

### 【画面③】スクラッチ（プログラミング）画面
* **機能:**
  * **GUIの実装:** プログラミング画面は自作せず、Google製の **「Blockly（react-blockly）」** を導入し、直感的なドラッグ＆ドロップUIを構築する。
  * **コマンド:** Blocklyのカスタムブロックとして「ループさせる動きブロック」や「セリフ（吹き出し）ブロック」を用意する。
  * 追加できるブロック（コマンド）の数は最大5個まで。
* **遷移トリガー:** 「放流」押下時、Blocklyで組み立てたブロック構造をJSONデータに変換し、APIへPOST送信。成功後、画面④へ進む（戻る操作は不可）。

### 【画面④】完了画面
* **機能:** 成功メッセージの表示。5秒経過後、自動的にStateを初期化し画面①（ホーム）へ戻る。

## 4. 大画面モニター（展示用画面）要件
* **目的:** 参加者が放流したキャラクターを受け取り、指定されたプログラムに従って画面内を泳がせる。
* **表示数の上限と管理:** 画面のパフォーマンス低下を防ぐため、**生き物の最大数は「30匹」**とする。
  * 31匹目が放流された場合、最も古いキャラクターを配列から削除する（FIFO: First In, First Out 方式）。
* **通信仕様:** バックエンドからのプッシュ通知（WebSocket等）を受け取り、リアルタイムに画面へ反映させる。

## 5. 今後追加が必要な機能・セーフティ要件（展示用暴走防止）
本番展示に向け、以下の機能を実装する。

* **【高優先】セーフティ機能（受付PC用キオスク設定）:** 
  * 右クリックメニューの禁止。
  * F5（リロード）やF12（開発者ツール）などのキーボード入力の無効化処理。
* **【低優先】管理者画面の追加:**
  * アプリの強制リセット（最初に戻る機能）などを備えた、スタッフ用の隠し画面の検討。
